# 《言弹交锋》W5.2｜真实嵌入尺寸可读性与动效节奏返修施工单

> **已被 W5.3 纠偏取代。** Owner 2026-09-24 明确：810×506 是 Codex 侧栏尺寸，不是游戏验收画布；
> 正式验收恢复 1440×900。后续不得再用本单的 810×506 放大字号结论指导桌面主画面。

> 施工对象：`game-rhetoric-duel` 当前引擎内版本  
> 关卡归属：W5 返修；W5.2 通过前不得进入 W6/W7 交付声明  
> Owner 反馈：抽牌、出牌过快看不清；左上、左下文字过小；右下按钮半透明、辨识度不足。  
> 验收主视口：DokiWorld 实际 iframe 内容区 **810×506 CSS px**，不是只看 1440×900 逻辑画布。

## 0. 裁定

接受返修。W5.1 的单元测试、构建和 1440×900 截图通过，只能证明实现没有技术回归，不能证明真实嵌入体验合格。当前宿主把 1440×900 整体缩放到约 `0.5625`：

- 逻辑 13px 的目标正文实际约 7.3px；
- 逻辑 11px 的意图、日志和卡牌正文实际约 6.2px；
- 逻辑宽 138px 的卡牌实际约 78px；
- “结束回合”实际约 115×25px，背景透明度约 0.14，文字视觉高度约 6.75px；
- W5.1 开局五张牌总演出约 690ms，出牌飞行约 300ms，仍快于玩家识读所需节奏。

所以本轮不是继续微调颜色，而是纠正验收坐标系：**所有字号、控件、卡牌尺寸与动画节奏都以真实 CSS 像素和真人可辨识时间验收。**

## 1. 架构边界与施工顺序

先走现有能力重组，不先扩引擎：

1. 为本游戏建立唯一 `RhetoricViewportSpec`，优先把逻辑舞台从 1440×900 收敛到同为 16:10 的 **960×600**，统一消费于 UI、play-field、卡位、飞行动画锚点和截图探针。
2. 禁止仅给 UI 套反向缩放、禁止自由 DOM/CSS、禁止在 `mountHost` 外再造第二套缩放器。
3. UI 继续只用 LayoutNode；play-field 继续只用引擎渲染组件和闭集 EffectKind。
4. 若 960×600 路线被现有公开契约阻断，必须留下“查了哪些 registry/手册、为什么重组失败”的原文，然后进入 owner A/B 裁决：
   - A（推荐）：PUI/宿主提供通用的“场景与 HUD 分层缩放或视口感知”能力；
   - B：游戏层手写 DOM/CSS/第二缩放器。B 违反 UI 铁律，不推荐且未获 owner 明示不得实施。

规则冻结：不得改卡表数值、抽牌规则、敌人意图、胜负条件、随机序列、SDK 契约和 simulation snapshot/hash。

## 4. W5.2-1｜真实尺寸布局重排

### 4.1 主验收阈值（实际 CSS 像素）

| 内容 | 810×506 下最低值 |
|---|---:|
| 主标题/敌人姓名 | 20px |
| 当前意图标题、关键数值 | 16px |
| 目标、意图、资源、日志正文 | 14px |
| 卡名 | 14px |
| 卡牌效果 | 12px |
| 次要来源/风味 | 11px；放不下可降级隐藏，不得挤压规则文本 |
| 按钮文字 | 14px |
| 主按钮命中高度 | 44px |
| 次按钮命中高度 | 40px |

以上是最终渲染后的实测值，不是设计 token 名称。任何关键交互文字低于阈值都算失败。

### 4.2 卡牌与信息区

- 810×506 下，手牌实际宽建议 104–118px，高 184–208px；五张牌必须可辨识，可适量重叠，但卡名、费用和效果不能被相邻牌遮住。
- 左上目标区最多三层：标题、目标正文、当前意图；正文不得落入 12px 以下。
- 左下资源区用稳定深色实底或高不透明渐变，不得让背景图穿透破坏对比度。
- 日志只显示最近一至两条；历史信息不得挤占资源或手牌空间。
- 右侧敌人进度和数值仍为强层级，避免为了放大左侧而压住敌人主体。

### 4.3 命令按钮

- 删除 `commandNode` 对 `skin: ''` 的显式覆写，恢复 `apolloBrocade` 的成熟按钮皮肤，除非 PUI 证明另一个现有 skin 更符合参考 demo。
- “结束回合”使用主按钮层级，实际背景不透明度至少 0.88、边框和文字对比度满足审计；实际宽至少 140px、高至少 44px。
- “认输/退出”可降级为次按钮，但不能使用近乎透明的 `rgba(..., 0.03)` 作为唯一辨识面。
- hover、pressed、focus-visible、disabled 四态必须截图或自动证据覆盖。

## 5. W5.2-2｜动画节奏返修

目标是“玩家能看清动作路径与结果”，不是单纯把所有数值乘二。

### 5.1 开局与补牌

- 单张入手：700–800ms；
- 相邻牌起飞间隔：110–140ms；
- 五张开局牌总演出：1.20–1.35s；
- 末张必须自然落位，表现 phase 不得提前截断 tween；
- 补牌使用相同运动语言，1–2 张时不得瞬移。

### 5.2 出牌

- 抬起/确认：120–180ms；
- 从真实点击卡位连续飞向目标：650–750ms；
- 命中强调与结果停留：250–400ms；
- 敌人回应/意图刷新：500–700ms；
- 起点必须来自被点击卡的真实卡位，禁止回到固定中心再飞；整段位置、缩放和透明度曲线连续。

### 5.3 输入与确定性

- 动画期间 busy 门继续阻止双提交与键鼠并发；不得吞掉已经提交的唯一动作。
- 动画只播放已提交结果，不能决定抽到什么、伤害多少或敌人选什么。
- 跳过、页面失焦恢复、reduced-motion 必须落到同一终态；reduced-motion 可缩短移动，但结果强调仍需清楚可读。
- 表现控制器测试必须断言每个 tween 的完成时间不晚于其 phase 结束时间。

## 6. W5.2-3｜自动化可读性探针

在本游戏测试/工具面增加 scale-aware 只读探针，至少输出：

- 宿主内容区宽高；
- 场景 transform scale；
- 目标正文、当前意图、资源值、卡名、卡效、主按钮文字的有效视觉字号；
- 五张卡实际矩形和相邻遮挡；
- 两个命令按钮实际矩形、背景 alpha 和文字对比度；
- 抽牌/出牌各阶段总时长与末 tween 完成时间。

它可以是本游戏专用测试或证据脚本，不得修改 `src/ui/**` 或伪造全局 UI 审计结论。

## 7. W5.2-4｜三视口验收

必须同时验证：

1. **810×506：主门禁**，全部可读性和按钮阈值必须通过；
2. 1024×640：不得出现遮挡、断行恶化或巨幅空洞；
3. 1440×900：不得因小屏修复而产生过大字体、牌位漂移或飞行终点错位。

每个视口至少保存 ready、deal-mid、play-flight、impact、disabled、end-state 六张图；810×506 另附一次完整开局抽牌和一次完整出牌录像/逐帧条。

## 8. 测试与撤修验红

施工人完成后：

- 本游戏全部测试；
- TypeScript；
- production build；
- `check-ui` 全套；
- `game-skill-audit`；

独立复查人必须至少做三次撤修验红：

1. 把舞台/缩放配置恢复为导致 0.5625 的旧值，有效字号门禁必须转红；
2. 把出牌飞行恢复 300ms、开局总时长恢复约 690ms，节奏测试必须转红；
3. 恢复 `skin: ''` 或旧透明按钮，按钮实测门禁必须转红。

撤修必须带锚点命中断言；恢复后全绿且工作区只含本单文件，才可 PASS。
