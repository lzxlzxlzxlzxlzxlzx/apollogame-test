# MC Fight R2：84单位数据装配施工单 v1.0

日期：2026-09-15。前置：owner确认S4完成。目标：将84种旧版单位一次性整理为新版可校验内容目录，为R3真实行为验证和全量试玩做准备。

## 1. 唯一输入

- [84张单位复原卡](r1-unit-cards-v1.json)：R2遍历入口。
- [旧版事实库](inventory/units.json)：由卡的 `legacyUnitIndex` 读取完整旧数据。
- [R1字段与冲突规则](r1-restoration-data-handoff.md)。
- [84行进度矩阵](full-restoration-matrix.json)。
- [单位玩法描述](unit-gameplay-descriptions.md)、[技能装配建议](unit-skill-loadouts-v0.1.md)、[战斗裁定](combat-rulings-v0.2.md)。

禁止重新从Unity工程散读数值、按单位ID写战斗分支，或直接把旧像素数值作为新版逻辑单位。

## 2. 本批必须完成

### 2.1 正式内容目录

在 `games/game-mcfight/content/` 下建立或扩展正式内容模块。具体文件名可遵从现有S4目录，但必须分开：

- `legacy-source`：只读旧ID、旧事实引用和素材引用。
- `adoption`：每项属性/技能参数的 `adopted | normalized | rebuilt | pending-design` 选择及理由。
- `units`：84个 UnitDefinition。
- `loadouts`：每单位完整 SkillLoadout 列表。
- `decisions`：84个 DecisionProfile。
- `presentations`：84个 PresentationProfile 槽，不把单姿态图标为动作完成。

运行时只读取新版 `units/loadouts/decisions/presentations`。旧版事实只能通过 `legacy-source` 和 `adoption` 溯源，不能直接影响战斗。

### 2.2 84个单位定义

每个 `r1-unit-cards-v1.json` 条目必须生成且仅生成一个UnitDefinition，保留 `legacyId`。定义至少含：

- 新版ID、名称、旧版ID、商店可见性、移动类别、基础标签、碰撞表现槽。
- 基础属性的新版值或 `pending-design` 显式标记。
- 价格、生命、速度、半径、目标资格、护甲/韧性字段的采用状态。
- 技能装配、决策和表现配置的有效引用。

6个旧版隐藏单位不可丢失；它们必须有正式定义，并在商店层标为 `hidden` 或明确召唤来源，不能被当成遗漏。

### 2.3 技能与决策装配

- 按单位复原卡的 `proposed.templates` 和 `proposed.decision` 建立装配；每项CD、范围、伤害、目标资格和表现语义有明确来源。
- 已由S2验证的共享模板优先复用。
- 同模板多单位、同单位多技能均须独立实例状态。
- 规则已确定的冲锋、俯冲窗口、前摇承诺、硬控打断、状态刷新、尸巫转化、轻语灵共享生命、龙卷/声波/吞噬等，不得在R2降级或遗漏。
- 不能由现有能力表达的项目统一登记为按“机制族”归类的缺口；不得临时写单位专属解释器。

### 2.4 素材与表现槽

- 全部84单位引用其旧 idle 主体图为身份候选，保留原路径和来源。
- 78张攻击图只登记为 `single-pose-candidate`；6个攻击图缺失；84个死亡图缺失。
- 每个技能都有动作语义、锚点、朝向/镜像和VFX/SFX槽；素材未完成时标 `missing`。
- `s6ArtBinding` 绝不因填入旧路径变成通过。

### 2.5 校验器和报告

新增R2内容校验，至少断言：

- 84张R1卡、84份定义、84份决策、84份表现配置一一对应。
- 所有ID唯一；所有引用存在；没有遗留S4专用单位表作为第二真相。
- 每个单位至少有一个技能或明确的“无主动攻击”行为。
- 每个新版数值都有 adoption 状态；`pending-design` 不能被运行时装配为假数值。
- 矩阵中的R2状态只能由校验后的真实结果更新。
- 同一输入两次生成内容摘要哈希一致。

输出 `docs/design/game-mcfight/r2-program-evidence.md`：内容计数、按技能机制族统计、pending列表、缺口列表、执行命令与退出码。

## 3. R2明确不做

- 不把84种单位全部宣称为已真实战斗验证；该项属于R3。
- 不做最终数值平衡和全量胜率调校；该项属于R4/S7。
- 不补14段或全量动作素材；该项属于S6。
- 不新增未裁定公共引擎能力或单位专属系统。
- 不修改策划验收剧本来适配实现。

## 4. 数值处理的硬规则

旧版 `effectiveAttributes`、`firstWinsParams` 和设计原文是事实记录，不能自动等于新版数值。

- 来源明确且新旧单位尺度已定义：填 `adopted` 或 `normalized`，给出换算依据。
- 旧值依赖bug、专属实现或与已确认新版规则冲突：填 `rebuilt`，给出原因。
- 没有统一换算依据、存在冲突或缺参：填 `pending-design`，不得用0、默认常量或静默回退伪装完成。

R2完成可以保留 `pending-design`，但必须逐项列出；R3/R4前由策划批量裁定。程序不替代策划决定最终平衡数值。

## 5. 交付顺序

1. 先读当前看板并确认S4人门已落账。
2. 建立内容目录和R2校验器，再导入84卡。
3. 分批装配基础单位、远程/飞行单位、复杂多技能单位、召唤/转换单位；每批跑同一校验器。
4. 汇总所有 `pending-design` 与能力缺口，不能边导入边偷偷补代码。
5. 运行R2定向测试、相关回归、类型检查、构建和完整组合审计。
6. 写证据、更新矩阵，交独立复查。R2并非流程板阶段，不代替S5/S6/S7/S8签核。

## 6. 完成判据

- 84/84单位定义、决策、表现槽和R1溯源存在且校验通过。
- 已知缺参、冲突和素材缺失全部可机读追踪。
- 没有单位专属战斗解释器或第二份单位事实表。
- R2报告能准确给出“已采用、重建、待策划、待能力、待美术”的数量与单位ID。
- 独立复查确认R2只扩内容数据和必要校验，没有越界改产品规则或共享引擎。
