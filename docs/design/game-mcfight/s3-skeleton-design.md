# MC Fight S3 游戏骨架设计 v1.0

日期：2026-09-15。状态：策划施工基线。适用阶段：S3 骨架关。

本文件冻结长期代码分层、数据归属、最小装配范围和验收口径。程序可按本文连续完成 S3，再统一自测并提交独立复查。本文不批准正式平衡数值，也不把 S4 的完整玩法循环提前算入 S3。

## 1. S3 的目标和边界

S3 要交付一个由正式入口启动、由真实引擎装载、能够渲染并响应一次操作的 MC Fight 编译期游戏骨架。它必须证明数据能被解释、实体能被创建、系统能运行至少两拍，且后续增加单位和技能不需要修改总架构。

本阶段包括：正式入口、薄宿主、世界装配、统一数据目录、三种代表单位、可观察的初始商店骨架状态、一个可点击信号、装载与引用验证。

本阶段不包括：完整购买经济、拖拽布阵规则、完整战斗胜负、敌军配军算法、84 单位正式数值、正式 UI、美术替换和性能优化。这些分别在 S4—S7推进。

## 2. 已冻结的产品入口

- 游戏 ID：`game-mcfight`；显示名：`MC Fight`。
- 交付形态：编译期游戏。S3 不另造卡带 manifest，也不把代码藏入 JSON。
- 启动后直接进入 `shop` 阶段，不显示主菜单。
- 正式阶段闭集：`shop → deploy → battle → result → shop`。
- S3 只真实显示 `shop` 骨架；阶段迁移在 S4 接通。不得为了演示伪造已经完成的购买或战斗结果。
- 启动、循环和卸载使用公共宿主能力；不另写第二套帧循环。

## 3. 长期分层合同

| 层 | 唯一职责 | 不得承担 |
|---|---|---|
| 入口/宿主 | 挂载、卸载、输入转信号、渲染快照 | 战斗判定、单位 ID 分支 |
| 游戏会话 | 当前阶段、局次、双方阵营、预算和回合结果 | 技能伤害公式、素材文件细节 |
| 内容目录 | 单位、技能模板、单位技能装配、决策、表现引用 | 实例 HP/CD/当前目标 |
| 世界装配 | 将目录翻译为已注册组件并安装 capability | 重写 capability 解释器 |
| 公共系统 | 索敌、技能阶段、移动、碰撞、伤害、死亡和状态 | 按具体怪物 ID 写特殊分支 |
| 表现适配 | 逻辑事件/状态到动作、特效、声音和挂点 | 决定命中、伤害、CD或攻击范围 |
| 运行实例 | HP、CD、目标快照、阶段、状态、施放序号 | 回写共享定义数据 |

依赖方向固定为：入口 → 会话/世界装配 → 内容目录与公共能力；表现只读取逻辑结果。内容目录不得反向引用宿主或页面元素。

## 4. 冻结的数据关系

数据对象名称可按仓库命名习惯调整，但关系和唯一数据源不得改变。

### 4.1 UnitDefinition

只保存单位身份和装配关系：`id`、显示文本引用、基础属性包、标签、碰撞/选择几何、`skillLoadoutIds`、`decisionProfileId`、`presentationProfileId`、商店元数据引用。

单位定义不得包含独立技能流程函数、动画文件路径、当前生命、当前目标或剩余 CD。

### 4.2 SkillTemplate

保存可复用的机制结构：目标资格、阶段结构、锁定/快照政策、打断政策、命中形态、效果种类、动作语义标识，以及允许由装配覆盖的参数白名单。

模板不绑定具体单位素材，也不保存某单位的最终伤害。CR01—CR15 的时序优先于模板默认值。

### 4.3 SkillLoadout

连接一个单位与一个技能模板，显式给出该单位版本的伤害、CD、施放距离、作用几何、阶段时长和效果参数。每项主动技能拥有独立运行状态；同模板跨单位复用时不共享 CD 或目标。

参数解析顺序冻结为：模板结构与默认值 → 装配显式值 → 合法战斗修正 → 本次施放快照。禁止从表现素材反推数值，也禁止同一伤害同时从两个字段来源计算。

### 4.4 DecisionProfile

保存公共决策器可解释的候选技能顺序/评分项、距离条件、目标条件和后备行为。它只能选择并启动 SkillLoadout，不复制目标合法性、CD或伤害算法。

### 4.5 PresentationProfile

保存动作语义标识到素材槽、逻辑挂点、默认朝向、镜像、允许缩放和阶段关键点的绑定。逻辑攻击几何是命中与调试轮廓的唯一来源；素材只对齐这份几何。

缺失的14段动作使用明确的缺失/占位状态，不得把旧版单姿态图片登记为已完成动画。

### 4.6 RuntimeState

实例状态由组件持有：生命、资源/CD、目标关系与施放快照、Flow 阶段、状态位、位置/速度、窗口意图、攻击区域及来源记录。共享目录必须只读。

## 5. S3 最小代表内容

S3 只装配三个代表单位，用于证明同一结构覆盖三条主链：

| 单位 | 代表能力 | S3 要证明 |
|---|---|---|
| 卫道士 | 地面单体近战 | 单位→装配→共享近战模板→表现语义引用完整 |
| 骷髅 | 地面远程弹丸 | 远程模板和近战使用同一目录/实例规范 |
| 恼鬼 | 飞行近战/俯冲窗口 | 飞行标签、窗口数据和表现配置可装配 |

这些单位沿用 S2 已验证的实验参数或重新声明为 `S3 fixture`，不得称为正式平衡值。S3 写入的每个字段都必须被装配器、校验器、渲染快照或明确测试读取；不用的字段不要提前填写。

## 6. 建议文件职责

程序可依仓库惯例微调文件名，但不得混合职责：

- `games/game-mcfight/game-mcfight.ts`：正式导出与薄宿主。
- `games/game-mcfight/content/`：单位、技能模板、装配、决策与表现目录。
- `games/game-mcfight/world.ts`：能力安装和实体装配。
- `games/game-mcfight/session.ts`：阶段闭集和会话初始状态。
- `games/game-mcfight/render.ts`：从真实世界/会话快照生成 S3 可观察画面。
- `games/game-mcfight/s3-*.test.ts`：装配、引用、实例隔离和两拍冒烟测试。

不得把已有 `s2-*.fixture.ts` 直接当正式内容目录。可以复用其已经进入公共引擎的能力与经过验证的装配方法。

## 7. S3 页面可观察合同

页面至少真实显示：游戏名称、当前阶段为商店、三个代表单位条目、其中一个单位的详情，以及骨架状态说明。显示数据必须来自正式内容目录，不得另写一份 UI 文案表冒充内容。

至少提供一个带真实动作标识的可点击控件，例如选择不同单位查看详情。点击后必须改变由会话状态驱动的可观察内容，供 S3 click probe 证明“信号打得穿”。这不是完整商店购买功能。

页面允许使用几何和文字占位，但必须明确标注开发骨架；不得把占位素材记录为 S6 完成。

## 8. 程序一次性交付清单

1. 将启动器中的 `game-mcfight` 从 `coming-soon` 接到正式动态导入。
2. 建立薄宿主、卸载清理和公共运行循环接线。
3. 建立第4节的只读目录与引用校验，装配第5节三个单位。
4. 安装 capability-plan 已批准且本骨架实际消费的能力；不安装无消费者的系统。
5. 显示真实 `shop` 初始状态并接通一次“选择单位查看详情”操作。
6. 加入测试：目录 ID 唯一、引用无悬空、三个单位可创建、共享模板实例隔离、装载后两拍不报错、卸载无残留。
7. 跑当前版本类型检查、相关测试、构建、完整能力组合审计和 S3 gate。
8. 写 `s3-program-evidence.md`，列出变更范围、命令与退出码、页面地址、截图/探针路径、剩余风险。
9. 交给非施工复查者按 S3 checklist 核证；复查通过后由 owner 人审。

## 9. 禁止项与退回条件

- 按怪物 ID 分支实现技能、索敌、伤害或动画逻辑。
- 复制 S2 fixture 成第二套正式战斗引擎。
- 新造未登记 capability、自由 DOM 或第二套运行循环。
- 为尚未确认的 D01—D12 填写并宣称正式规则。
- 页面显示的数据与真实目录、组件或关系不一致。
- 存在填入却没有消费者的字段、悬空 ID、共享可变模板状态或卸载残留。
- 用单姿态图片冒充14段动作已经完成。

出现公共能力缺口时，程序必须给出具体规则、现有能力核查和最小 A/B 方案，登记缺口后停止该依赖项；不因单个缺口暂停其余独立施工。

## 10. S3 完成定义

同时满足以下条件才可提交人审：

- 正式启动入口可打开，非 `coming-soon`，无控制台错误。
- 三个代表单位均由统一目录装配，世界能运行至少两拍。
- 选择单位操作能改变真实会话状态和画面。
- 类型检查、相关测试、构建、能力组合审计与 `gate game-mcfight S3` 全绿。
- 渲染探针和点击探针留有当前内容指纹对应的证据。
- 独立复查逐项确认：编译期形态无需卡带 manifest；其余数据没有代码走私、用途与 capability-plan 一致、无死数据。

S3 通过只表示骨架稳定。随后 S4 按已冻结的数据结构完成最小闭环：商店购买→拖拽部署→PvAI战斗→结算→重新购买，并由策划先提供至少三个验收剧本。

## 11. 减少返工的变更规则

从 S3 开始，变更分三类：

- 新增单位、装配参数或表现绑定：只扩内容目录，不改公共系统。
- 新增已支持的技能组合：新增模板/装配数据并补组合测试，不按单位写代码。
- 出现现有 schema/capability 无法表达的新规则：先改设计与能力计划或登记缺口，经过裁决后再改底座。

程序可以按本文一次完成 S3。后续阶段仍需分别过门，因为真实试玩、UI结构和美术验收无法由骨架测试预先替代；这不是反复重做，而是在同一骨架上逐层补齐。
