# 索敌与单位技能状态机：现有引擎核查

2026-09-09。仅分析与现有测试验证，未修改引擎或裁决新增能力。

## 结论

现有引擎具备感知、目标关系、移动、状态存储、条件规则、流程机、行为树求值、技能模板生成等基础。尚未发现可直接配置并统一处理多单位技能前摇/持续/后摇、独立冷却、目标锁定与打断清理的完整战斗技能执行器。不能把注册名为caster或state当成完整技能系统的证据。

## 与MC Fight需求的关系

1. 简单最近敌人：可直接复用aggro基础。
2. 地面近战只选地面或俯冲中的敌方单位：可探索投影成阵营+可攻击类别的专用组合标签，但不能把两个独立bit直接OR后当AND使用；还需验证标签更新、查询缓存和技能命中时复核。
3. 普攻追击目标与技能锁定目标分离：当前单位Relation只有一份。可研究技能实例实体承载自己的目标，但需验证动态归属、模板引用和回放，而非擅自认定无解。
4. 目标保持、最低生命选择、技能筛选：已读aggro入口未提供，先尝试现有组合并实证，再列正式缺口。
5. 多单位技能FSM：State+SelfRule+Timer/Flow有表达基础，但不能把全局状态名和计时器直接用于多只同种怪物。要验证每个实例独立状态、冷却和转移，避免同步串扰。
6. 同名施法信号：多个Caster监听相同名称会一起响应；需实例寻址或经验证的本地触发组合，不能在批量单位中直接广播cast。

## 建议的架构职责（提案）

- 感知层：公共空间查询与目标合法性/排序，产生候选目标。
- 决策层：选择移动、普攻、技能；复杂优先级才使用BT，不用BT承担持续施法。
- 执行层：单位独立技能实例，保存技能阶段、计时、施法时锁定的对象/坐标/方向，以及打断处理。
- 效果层：复用prefab、launch、hitbox、状态等既有部件。

俯冲技能阶段可讨论为待机→准备→俯冲/命中→恢复→升空。可受地面攻击的窗口应由阶段数据明确控制，并统一供索敌与命中复核消费。具体从哪一阶段进入、何时退出、被控制后怎么办尚未确定。

窗口条件若由时序分散的全局信号控制，会产生状态已变而可攻击标签尚未更新的间隙；应明确这些变化的生效拍及优先级。

## 下一步验证建议

先用“两只同种飞行怪+地面近战”的场景尝试纯现有组合：各自不同时间俯冲、不串状态或计时；仅窗口内可反击；目标死亡与施法被打断后正确退出；重开不残留；同seed同输入重复结果一致。

若现有组合可表达且清楚，保留组合；若只能依靠大量全局ID和信号拼接，则提出A扩展通用目标选择/技能执行能力，B受控游戏例外，各附代价，按项目协议由owner裁决。本次仅推荐优先复用或通用扩展，不宣布缺口已经批准。
