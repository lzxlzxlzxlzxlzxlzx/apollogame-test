## 二、他点名要我盯的两处

### 2.1 trace 折叠 —— ❌ **会吞掉整条**（新伤 M1·P1）

复现（挂 `DebugTrace`，跑一拍，数 `system === 'flow-field'` 的事件）：

```
[A] 全员 fieldId 打错（4 个）→ flow-field trace 条数 = 0
[B] 全员在网格外（3 个）    → flow-field trace 条数 = 0
[C] 1 个打错 + 1 个正常     → trace 条数 = 1
    · [commit] 写 Velocity：1 走 / 0 停 || why=场 1 张 · 停的原因：1 个找不到自己的场（查 FlowAgent.fieldId 与 FlowField.id 对没对上）
```

根因在折叠的**门**上，不在折叠本身：

```ts
if (moved > 0 || stopped > 0) {            // ← noField / offGrid 两类都不加这两个计数
  ...  why.push(`${noField} 个找不到自己的场…`) ...
}
```

`noField++` 与 `offGrid++` 各自 `continue`，既不进 `moved` 也不进 `stopped`。
所以**"一个单位都没动起来"这个最该喊一声的情形，恰好是唯一一声都不喊的情形**。
折叠之前它有 `${noField} 个单位找不到自己的场 → 停` 这一条。

这正是日志基准守则点名的那条红线（「凡『什么都没发生』的分支必须记」），而且 `fieldId` 打错
是数据驱动面上**最常见**的一种错。

**他的用例抓不到的原因**：那条用例的世界里永远有走得动的单位（`ok1/ok2/plain`），
所以 `moved > 0` 恒成立，`commit` 恒发，`why` 里的分项恒在。

**修法（一行，我验过）**：门改成 `moved > 0 || stopped > 0 || noField > 0 || offGrid > 0`。
应用后：

```
[A] 全员 fieldId 打错（4 个）→ trace 条数 = 1
    · [commit] 写 Velocity：0 走 / 0 停 || why=场 1 张 · 停的原因：4 个找不到自己的场（…）
[B] 全员在网格外（3 个）    → trace 条数 = 1
    · [commit] 写 Velocity：0 走 / 0 停 || why=场 1 张 · 停的原因：3 个在网格外（…）
```

我把这一行当 sabotage 打进去（X4）跑点名测试：**68 测全绿**——证明它不破坏任何现有判据，
也**反证了现有判据看不见这个 bug**。顺带：`0 走 / 0 停` 这一条挂 `commit` 语义上别扭，
建议 `noField+offGrid > 0 && moved+stopped === 0` 时发 `reject`。

**另一条同源的丢法（M7·P2）**：配置类留痕改成只在 `rebaked > 0` 那拍发，
而**后加**一张同 id 的场不会触发重铺 ⇒ 永远不留痕：

```
[D] 同 id 的场后来才加入 → 「同 id」留痕条数 = 0（总 trace 7 条 = 7 拍 × commit）
```

`los` 那条是场自带的字段（一开始就在，首拍必报），所以只有 `dupes` 有这个形态。
建议 `dupes` 的判据条件改成「场集合的 id 多重集变了」而不是「重铺了」。

### 2.2 LP3 暴力搜的容差 0.02 —— **容差本身没问题；弱在只跑一个场景**（M4·P2）

先量真实差距（`worstViolation(LP3) − 暴力最优`）：

```
[LP3-a] 用例场景：LP3 违反量 0.300000 · 暴力最优 0.300000 · 差 0.000000 · 容差 0.02
        LP2 落点违反量 1.300000（差 1.000000）⇒ 0.02 只占「LP2 vs 最优」距离的 2%
[LP3-b] 173 个随机无可行解场景：LP3−暴力最优 中位 −0.004215 · p90 −0.001417 · 最大 −0.000296
        （负数 = LP3 比 120 步暴力网格还优，即 LP3 基本是精确的）
```

**所以 0.02 不松**：真实差距是 0（甚至负），而要抓的失效（退回 LP2 落点）差 1.0 = 容差的 50 倍。
两把针对性的刀也证明它有牙：**X1（LP3 投影线方向翻转）与 X2（LP3 优化方向翻转）现在都恰红**——
而上一轮这两刀里 X1 **完全没被镜像断言抓到**。换成暴力搜是这一轮最实的一处改进。

**弱点在样本量**：把 LP3 的推进阈值加一个 epsilon（`> distance` → `> distance + 0.015`，
非常像"加个浮点余量"的手误），**68 测全绿**；加到 **0.03（已经大于容差 0.02）仍然全绿**。
因为**那一个场景的答案不动**（违反量还是 0.300000），而随机场景上差距已经出现（0.015 那刀实测最大 +0.0079）。

**修法**：把暴力对照跑到**一族随机无可行解场景**上（复用环形搜索用例里那套 LCG 种子写法），
一个手搭的对称环挡不住阈值类手误。

## 三、他让我复核的根因判断 —— ❌ **两条排除实验里有一条不可复现**（新伤 M3·P1）

他的结论：中场那 8% 穿模是「离散时间 + 限速下的**固有边界**」，依据是排除了 `maxNeighbors` 与 `timeHorizon`。

**`maxNeighbors` 那条我复核属实**（他说"不变甚至略差"）：

```
[N1-c] maxNeighbors= 8 → worstMid=0.64442     ← 出厂
[N1-c] maxNeighbors= 9 → worstMid=0.63113
[N1-c] maxNeighbors=12 → worstMid=0.63113
[N1-c] maxNeighbors=20 → worstMid=0.63113
```

**`timeHorizon` 那条不成立。** 他写「16/24 与 8 逐位相同」，实测逐排布全不同、而且 16 明显更好：

```
[H8]  mid: 0.70090 0.68053 0.64442 0.67791 0.67336 0.69664   worstMid=0.64442
[H16] mid: 0.70012 0.70044 0.69183 0.69308 0.70143 0.70515   worstMid=0.69183  ← +7.4%
[H24] mid: 0.68911 0.68221 0.70004 0.70047 0.70000 0.69848   worstMid=0.68221
[H8]  end: 0.70004 0.70000 0.71280 0.70260 0.70350 0.70029
[H16] end: 0.70006 0.70000 0.70095 0.70005 0.70273 0.71147
[H24] end: 0.70160 0.65551 0.63173 0.70050 0.70002 0.70001   ← end 反而塌了
```

`timeHorizon = 16` 把中场穿模从 8% 压到 1.2%，**基本把那条"守不住"的缺口补上了**；
`24` 又转坏（终点区塌到 0.63173）。所以 8 不是"边界所在"，是**这个旋钮没调过**，
而且它**非单调**——恰好证明"扫一族"这个方法论是对的，只是他扫的是排布、没扫这个旋钮。

**我另做了一个他没做的实验：细化时间步**（速度与前瞻同比缩放 ⇒ 物理前瞻距离不变，只是一拍更小）：

```
[N1-e] 一拍缩小 1× (speed=0.5000 horizon= 8) → worstMid=0.64442
[N1-e] 一拍缩小 2× (speed=0.2500 horizon=16) → worstMid=0.68042
[N1-e] 一拍缩小 4× (speed=0.1250 horizon=32) → worstMid=0.69543
[N1-e] 一拍缩小 8× (speed=0.0625 horizon=64) → worstMid=0.69605
```

**离散化解释了大部分但不是全部**（收敛到 ~0.696，不是 0.70），**而且在出厂拍长下那 8% 是可以拿回来的**。
所以准确的判词是：「中场穿模里有**一部分**是离散时间的固有代价（约 0.4%），
**其余大部分是 `ORCA_TIME_HORIZON = 8` 这个缺省值偏小**——这是个活旋钮，不是边界。」

**修法**：把「固有边界」这句改口（`orca.ts` 文件头 / `spatial.ts` / 调研 §10 / 两个池子条目）；
把 `timeHorizon` 8 vs 16 的开销/观感权衡**明确交给 Demo 定档**（16 会让邻域半径翻倍 ⇒ 见 §6 性能）。
