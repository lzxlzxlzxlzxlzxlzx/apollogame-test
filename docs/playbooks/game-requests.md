# 游戏需求单手册（当前控制面，不是历史日志）

## 一句话

`docs/design/<game>/requests.md` 只回答四件事：**现在要守什么、正在做什么、卡在哪里、证据去哪看**。施工过程、测试明细和已结束工单必须分流，禁止靠不断追加时间线维护状态。

## 文件职责

| 内容 | 唯一去向 |
|---|---|
| 当前产品/合同/冻结约束 | `requests.md`；稳定后应归并到 `brief.md`、原型说明或 SDK 文档，当前单只留链接 |
| 当前活动工单、阻塞、owner A/B 待裁决 | `requests.md` |
| 完整施工规格（确实放不下时） | `work-orders/<ticket-id>.md`；当前单只留摘要和链接 |
| 机器命令、退出码、撤修验红、独立复查 | `review/<stage-or-ticket>.md` |
| 真渲染、截图、逐项对齐 | `self-check/<stage>-alignment.md` 与 `self-check/shots/` |
| 流程阶段状态 | `pipeline.json` / 项目路线图控制台；不得复制一份口头状态冒充权威 |
| 已完成、取消、替代的全文 | `archive/`；只供追溯，不是后续施工依据 |

## 必须使用的当前单结构

新建或重构从 `docs/playbooks/templates/game-requests.template.md` 起步，顺序固定：

1. 当前结论；
2. 当前有效约束；
3. 当前活动工单；
4. 阻塞与待 owner 裁决；
5. 证据索引；
6. 归档入口。

没有内容的章节写“无”，不要用历史材料填满。每张活动工单只保留：ID、目标、验收判据、允许/禁止边界、施工主体、状态和证据链接。

## 禁止写入 `requests.md`

- 日报式“某日做了什么”的追加时间线；
- 完整终端输出、测试列表、退出码流水账；
- 截图采集过程和浏览器操作记录；
- 施工回执、独立复查全文、撤修验红全文；
- 已完成阶段的完整工程单；
- 同一 owner 判词在多处重复粘贴；
- 被新方案替代的旧规格正文；
- 为了“保留历史”而复制 review/self-check/pipeline 已有内容。

## 生命周期

### 新增

- 先检查是否已有等价工单或已有 capability；重复项直接链接，不再复制。
- 确需新增时，只写可验收的当前规格；长于一屏的实施细节拆入 `work-orders/`。
- capability gap 同步登记 `capability-gaps.json`，但当前单只保留裁决摘要和 ticket 链接。

### 施工中

- 更新原工单的单一 `状态` 字段，禁止在底部再追加一份“最新进度”。
- 测试和复查证据直接写对应 `review/` / `self-check/`，当前单只更新链接。
- 需求发生变化时原地修改当前规格；若语义已被替代，把旧全文归档并只保留新规格。

### 完成、取消或替代

- 同一回合把工单正文从当前单移除。
- 长期仍影响产品的结论写入权威设计/合同文档；当前单最多留一行结论和链接。
- 只有确有审计价值时才把原文移到 `archive/`；归档文件头必须声明“历史证据，不是当前施工依据”。
- 禁止把“完成回执”继续堆在原工单后面。

## 预算与旧文件棘轮

- 新/已整理游戏当前单遵守 `context-budget-baseline.json` 的统一字符与行数上限；超限正解是拆分和归档，禁止抬预算迁就流水账。
- 已超过新上限的旧文件使用逐文件兼容上限：只能不增长；每次触碰必须顺手缩减。降到统一上限后删除对应兼容项，不得重新放宽。
- 预算绿只证明“读得下”，不证明内容职责正确；review 仍须检查本手册的禁写项。

## 收工检查

- 当前单能否在一分钟内回答“下一张工单是什么”？
- 是否存在 review/self-check 已有、当前单又重复的证据？
- 是否仍保留 done/wontfix/superseded 的完整正文？
- 是否只有一个当前状态，而不是多段互相冲突的时间线？
- `node scripts/context-budget-guard.mjs` 是否没有新增游戏需求单问题？

任一答案不合格，先整理需求单再交接。
